# Walkthrough: Connecting to a LangGraph Deployment

> **Notebook:** `connecting.ipynb`
> **Goal:** Use the LangGraph SDK to interact with the deployed `task_maistro` graph — runs, threads, and the cross-thread memory store.

---

## The Big Picture

Once the deployment is running at `http://localhost:8123`, you interact with it through an HTTP API. LangGraph exposes three conceptual groups of endpoints:

| Group | What it models |
|-------|---------------|
| **Runs** | A single execution of the graph |
| **Threads** | A conversation (many turns, one `thread_id`) |
| **Store** | Long-term memory shared across threads |

You can hit the raw API (documented at `http://localhost:8123/docs`), but the SDK gives you a cleaner Python interface.

---

## 1. Two Ways to Connect

### SDK (`langgraph_sdk`)

```python
from langgraph_sdk import get_client

client = get_client(url="http://localhost:8123")
```

The SDK wraps every API endpoint as an async method (e.g., `client.runs.create`, `client.threads.get_state`). Use this when you control the client code.

### RemoteGraph (`langgraph`)

```python
from langgraph.pregel.remote import RemoteGraph

remote_graph = RemoteGraph("task_maistro", url="http://localhost:8123")
```

`RemoteGraph` makes the deployed graph look like a local `CompiledGraph`. It supports `.invoke`, `.stream`, etc. Use this when you want to drop a remote graph into existing code that already calls a local graph.

## 2. Runs

A **run** is one execution of the graph. Each run gets a unique `run_id`, and its result is stored in Postgres.

### Background run (fire-and-forget)

```python
thread = await client.threads.create()
run = await client.runs.create(
    thread["thread_id"],
    "task_maistro",
    input={"messages": [HumanMessage(content="Add a ToDo to book flights.")]},
    config={"configurable": {"user_id": "test"}},
)
```

`client.runs.create` returns immediately with the run metadata. The graph continues running in the background. Check its status with:

```python
run_info = await client.runs.get(thread["thread_id"], run["run_id"])
print(run_info["status"])  # "pending" -> "success" / "error"
```

### Blocking run (wait until done)

```python
await client.runs.join(thread["thread_id"], run["run_id"])
```

`join` blocks until the run completes. Useful when you need the result before continuing.

### Streaming tokens

```python
async for chunk in client.runs.stream(
    thread["thread_id"],
    "task_maistro",
    input={"messages": [HumanMessage(content="What should I focus on?")]},
    config=config,
    stream_mode="messages-tuple",
):
    if chunk.event == "messages":
        print("".join(
            item["content"] for item in chunk.data if "content" in item
        ), end="", flush=True)
```

`stream_mode="messages-tuple"` streams tokens as they are generated by the LLM. The server publishes updates to Redis; the SDK subscribes and forwards them to you. This is the production pattern for chat UIs.

## 3. Threads

A **thread** stores all the checkpoints from every run that shared the same `thread_id`. It is the unit of multi-turn conversation.

### Check thread state

```python
state = await client.threads.get_state(thread["thread_id"])
for m in convert_to_messages(state["values"]["messages"]):
    m.pretty_print()
```

Returns the latest checkpoint: all messages accumulated across every run on this thread.

### Copy (fork) a thread

```python
copied_thread = await client.threads.copy(thread["thread_id"])
```

Creates a new thread with the same history but a different `thread_id`. Subsequent runs on the copy are independent — they don't affect the original thread. Useful for branching experiments.

### Human-in-the-loop: edit state and resume

The server stores every intermediate checkpoint. You can pick any checkpoint, edit the state, and re-run from there.

```python
# 1. Get the thread history (most-recent first)
states = await client.threads.get_history(thread["thread_id"])
to_fork = states[-2]  # pick an earlier checkpoint

# 2. Edit the state at that checkpoint
forked_input = {
    "messages": HumanMessage(
        content="Give me a summary of ToDos due next week.",
        id=to_fork["values"]["messages"][0]["id"],  # supply the ID to OVERWRITE, not append
    )
}
forked_config = await client.threads.update_state(
    thread["thread_id"],
    forked_input,
    checkpoint_id=to_fork["checkpoint_id"],
)

# 3. Resume from the new checkpoint
async for chunk in client.runs.stream(
    thread["thread_id"],
    "task_maistro",
    input=None,  # no new input — resume from the checkpoint
    config=config,
    checkpoint_id=forked_config["checkpoint_id"],
    stream_mode="messages-tuple",
):
    ...
```

**Key detail:** the `messages` reducer appends by default. To *overwrite* a message instead of appending, supply the existing message's `id`. Without the `id`, you'd end up with two messages.

## 4. Cross-Thread Memory (Store)

The `task_maistro` graph uses the LangGraph memory store (`BaseStore`) to save ToDos, profiles, and instructions namespaced by `user_id`. The deployment backs this store with Postgres, so it persists across threads and restarts.

The SDK gives you direct access to the store outside the graph.

### Search items

```python
items = await client.store.search_items(
    ("todo", "general", "test"),  # namespace tuple
    limit=5,
    offset=0,
)
```

The namespace `("todo", "general", "test")` matches the `configuration.py` defaults: `todo_category = "general"`, `user_id = "test"`.

### Add items

```python
from uuid import uuid4

await client.store.put_item(
    ("testing", "Test"),
    key=str(uuid4()),
    value={"todo": "Test SDK put_item"},
)
```

`put_item` is how you inject data into the store directly, without going through the graph. The graph uses `store.put(...)` internally; this is the SDK equivalent.

### Delete items

```python
await client.store.delete_item(
    ("testing", "Test"),
    key="<the-key-uuid>",
)
```

---

## What to Understand Here

1. **Run vs. Thread** — a run is one graph execution; a thread accumulates checkpoints across many runs. You pass `thread_id` to link runs together into a conversation.
2. **Three stream modes** — fire-and-forget (create only), blocking (create + join), streaming (create + stream). Pick based on whether the client needs the result in real time.
3. **Forking works because of checkpoints** — the server saves the full state at every node. `update_state` writes a new checkpoint on top of an old one, and `checkpoint_id` tells the server where to resume from.
4. **The store is independent of threads** — ToDos saved in the store persist across all threads for a given `user_id`, which is how cross-session memory works in `task_maistro`.
